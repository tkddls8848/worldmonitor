# 프론트 경량화 설계 (3D 지구본 제거 + 측정 기반 최적화)

상태: 초안 (2026-11-21)
선행: 1단계 완료(`2026-11-15-three-layer-simplification-design.md`). 이 작업은 2단계 재배치(`web/`, `backend/`, `connectors/`)보다 먼저 한다.

## 1. 의도

주인이 원하는 것은 두 가지다.

1. 브라우저에서 대시보드가 빨리 뜬다.
2. 여러 컴포넌트의 상호작용 결과가 지연 없이 바로 화면에 보인다. 예를 들어 지도에서 나라를 누르면 국가 패널이 열리고, 레이어를 켜면 지도에 나타난다.

지금 있는 기능은 그대로 유지한다. 예외는 하나다. 주인이 필요 없다고 정한 3D 지도는 뺀다.

## 2. 목표, 비목표, 반목표

**목표**

- 3D 지구본 렌더러와 2D/3D 전환을 없앤다.
- 로드와 상호작용 지연을 숫자로 재는 장치를 만든다. 그 장치로 개선을 증명한다.
- 측정에서 가장 나쁜 곳부터 고친다.

**비목표**

- 화면 프레임워크를 바꾸지 않는다. 지금은 프레임워크 없는 TypeScript와 일부 Preact다. Vite도 유지한다. 측정 결과 원인이 프레임워크로 드러나지 않는 한 그대로 둔다.
- 파일 재배치는 하지 않는다. 그것은 2단계에서 한다.
- 데이터 수집 주기와 서버 쪽 성능은 다루지 않는다. 단, API 응답이 화면 지연의 원인으로 측정되면 다룬다.

**반목표.** 아래 중 하나라도 생기면 숫자가 좋아져도 실패다.

- 기능이 소리 없이 사라진다. 패널, 레이어, 조작, 국가 브리프, 채팅 분석, 시나리오, CII 표시가 예다.
- 화면을 빨리 띄우려고 데이터를 낡거나 비어 보이게 만든다.
- 패널을 늦게 불러오다가 첫 조작 때 오히려 기다리게 만든다. 지연을 옮겼을 뿐 없애지 않은 경우다.

## 3. 제약

- 개인 모드다. `npm run build:personal`로 빌드하고 `npm run start:personal`로 띄운다. 127.0.0.1:3000 앞단은 HTTP Basic 인증을 거친다.
- 한 대의 Windows 개발 PC에서 돈다. 메모리가 부족해 서버가 강제 종료된 적이 있다. 측정 장치는 무거운 동시 실행을 피한다.
- CI의 Linux Test에는 원래 있던 실패 37개가 있다. 새로 깨지는 테스트는 0개여야 한다. 기준은 최신 Test 실행의 실패 이름 집합이다.
- AGENTS.md 규칙을 따른다. main에 바로 커밋하고 origin에 푸시한다. 브라우저 import 방향 규칙(`lint:boundaries`)과 `bundle:check` 예산을 지킨다. 예산을 바꾸면 같은 커밋에서 갱신한다.

## 4. 접근 방법

| 방법 | 내용 | 판단 |
|---|---|---|
| **A. 측정 후 고치기 (선택)** | 측정 장치를 먼저 만들고, 가장 나쁜 곳부터 고쳐 다시 잰다 | 기능을 그대로 두고 빠르게 할 수 있는 유일한 길. 주인이 선택 |
| B. 가벼운 프레임워크로 다시 쓰기 | 컴포넌트 223개를 새로 짠다 | 원인이 프레임워크가 아니라 지도 라이브러리와 시작 시 하는 일로 보여 효과가 불확실. 기능이 바뀔 위험이 큼 |
| C. 기본값 바꾸기 | 예: 무거운 기능을 기본으로 끈다 | 사용 경험이 바뀜. 3D 지도만 주인 결정으로 이 방식(제거)을 적용 |

## 5. 정해진 부분

### 5.1 3D 제거 (주인 결정)

없애는 것:

- 3D 지구본 렌더러: `src/components/GlobeMap.ts`와 globe.gl과 그 아래 three.js 의존성.
  - 빌드 산출물 `GlobeMap-*.js`가 약 1.8MB다.
  - 지구본 텍스처(`public/textures`, 약 3.4MB)는 지구본만 쓰면 함께 지운다.
- 2D/3D 전환 UI와 그 상태:
  - `src/app/map-dimension-control.ts`
  - 설정의 지도 차원 선택
  - 저장된 `globe` 선호값
  - 에이전트 명령의 `globe` 대상: `agent-bus-applier.ts`의 `globe_unavailable` 경로
  - `src/bootstrap/globe-marker-probe.ts`
- 지구본 전용 테스트. `tests/dom/globe-*`처럼 대상이 사라지는 테스트가 해당한다.

내 판단으로 함께 없애는 것:

- 평면 지도(DeckGL)의 기울이기와 회전, 즉 `VITE_MAP_INTERACTION_MODE=3d`.
  - 평면 전용(`flat`)으로 고정하고 환경 변수를 없앤다.
  - 이유: 주인이 "3D 지도는 필요 없다"고 했다. 이 기능은 라이브러리를 더 불러오지 않으므로 무게에는 영향이 없다.
  - 주인이 남기라고 하면 이 항목만 되돌린다.

남기는 것:

- 데스크톱의 DeckGL/MapLibre 평면 지도.
- 모바일과 저사양 기기용 SVG 지도(`Map.ts`). 둘 다 지금 기능이다.

저장된 선호값이 `globe`인 브라우저는 평면 지도로 열려야 한다. 오류나 빈 지도가 되면 안 된다.

- 데스크톱은 DeckGL 평면 지도로 연다.
- 모바일은 지금 기본값인 SVG 지도로 연다. 3D를 고른 고사양 휴대폰도 이쪽으로 간다. (내 판단)

에이전트용 인터페이스의 `3d`/`globe` 값도 정리한다. (내 판단)

- 해당 위치: `webmcp-map-layer-catalog.ts`의 렌더러·필터 값, `search-manager.ts`가 지구본으로 보내던 명령, `agent-bus-applier.ts`의 지구본 대상.
- 처리: 목록에서 `3d`를 뺀다. 지구본을 요청받으면 지금의 `globe_unavailable` 거부 결과를 돌려준다. 조용히 평면으로 바꾸지 않는다. 호출한 쪽이 결과를 보고 알 수 있어야 하기 때문이다.
- 지구본 전용 설정 `globe-render-settings.ts`도 함께 없앤다.

### 5.2 측정 장치

- **명령:** `npm run perf:personal`. 이미 실행 중인 개인 서버를 대상으로, 시스템에 설치된 Chromium을 Playwright로 띄운다. 인증 정보는 `.env.local`에서 읽고 출력하지 않는다.
- **로드 지표** (대시보드 첫 진입, 캐시 비운 상태와 캐시 있는 상태를 각각 잰다):
  - FCP와 LCP
  - 지도 준비 시점: 렌더러가 첫 프레임을 그린 때. 앱의 `wm:map:renderer-demand` 표시에서 둘로 나눠서도 기록한다(`mapDemand`: 첫 그리기 뒤 일부러 두는 대기가 끝나 DeckGL 로드를 시작한 때, `mapAfterDemand`: 그때부터 지도 준비까지)
  - 첫 화면 패널에 데이터가 찬 시점
  - 긴 작업 합계(Total Blocking Time)
  - 전송된 JS/CSS 바이트
  - JS 힙 크기
- **상호작용 지표.** 브라우저 Event Timing API로 입력에서 다음 화면 그리기까지의 시간을 잰다(INP 방식). 대상 조작은 다음과 같다.
  1. 지도에서 나라 클릭 → 국가 패널 표시
  2. 레이어 켜기/끄기 → 지도 반영
  3. 패널 열기와 탭 전환
  4. 검색 창(⌘K) 열기와 입력
  5. 대시보드 변형 전환. 개인 빌드에서 쓰는 경우에 한한다.
- **반복과 기록.** 각 측정을 5회 돌려 중앙값을 낸다. 결과는 `.personal/perf/<라벨>.json`에 저장한다. `-- --compare <라벨A> <라벨B>`로 두 결과를 비교표로 본다.
- **측정 절차 변경 (가 단계 최종 리뷰 반영).**
  - 측정하는 5회 앞에 버리는 예열 1회를 먼저 돌린다(`--warmup`, 기본 1). 서버가 처음 응답하는 첫 회의 튀는 값이 표본에 들어가지 않게 하려는 것이다.
  - 결과 파일에 지표별 요약과 함께 회차별 원래 값(`samples`, 실패는 `null`)을 남긴다.
  - 레이어 조작의 결과는 앱이 그 레이어를 넣은 deck 레이어 목록을 지도에 넘긴 뒤 WebGL 그리기가 한 번 일어난 때로 본다. 주소창의 `layers` 값은 앱이 250ms 디바운스로 쓰므로 보지 않는다.
  - 이 변경 전의 결과(`baseline-rerun`, `no-globe` 등)는 예열 없이, 레이어는 주소창 기준으로 잰 것이다.
- **CI 미포함.** 실데이터가 든 서버가 있어야 하므로 CI에는 넣지 않는다. 대신 번들 크기는 기존 `bundle:check` 예산으로 CI에서 지킨다.
- **측정 대상 (내 판단).**
  - 주로 데스크톱 DeckGL 경로를 잰다. 개인 서버는 루프백에만 묶여 있어 실제 사용 환경이 이 PC의 데스크톱 브라우저이기 때문이다.
  - 같은 측정을 CPU 4배 감속으로 한 번 더 돌린다. 메모리가 빠듯한 PC에서 숨은 긴 작업을 드러내기 위해서다.
  - 모바일 SVG 경로는 재지 않는다. 기능 테스트로만 지킨다.
- **잡음 통제 (내 판단).**
  - 측정 중에는 수집기를 돌리지 않는다. 비교하는 두 측정은 같은 서버 실행 안에서 연달아 잰다.
  - 데이터 상태가 측정 사이에 바뀌지 않게 하려는 것이다. 응답을 녹화해 재생하는 방식은 장치가 커져서 쓰지 않는다.
  - 변경을 "효과 있음"으로 치는 조건은 두 가지를 모두 만족할 때다. 해당 지표의 중앙값이 10% 이상 좋아지고, 그 차이가 5회 측정의 흩어짐(최솟값~최댓값 범위)보다 커야 한다.
  - 둘 중 하나라도 못 미치면 되돌린다. 3D 제거는 주인 결정이므로 측정과 상관없이 유지한다.

### 5.3 개선 반복

작업은 두 단계로 나누고, 그 사이에 주인 확인을 한 번 받는다. (내 판단)

1. **가 단계**
   - 측정 장치를 만든다.
   - `baseline`을 잰다.
   - 3D를 제거한다.
   - `no-globe`를 잰다.
   - 두 결과와 가장 느린 항목 목록을 주인에게 보여 주고, 6절의 성공 기준 숫자를 확정한다.
2. **나 단계**
   - 확정된 숫자를 종료선으로 삼아 아래 반복을 한다.
   - 종료선에 닿으면 멈춘다.
   - 종료선에 닿지 않았는데 측정으로 확인되는 개선 항목이 더 없으면, 남은 차이와 그 원인을 보고하고 멈춘다.

- 기준선(`baseline`)을 먼저 잰다. 그다음 3D 제거 후(`no-globe`)를 잰다.
- 이후 측정 결과의 가장 나쁜 항목부터 하나씩 고치고, 고칠 때마다 다시 잰다. 효과가 없는 변경은 되돌린다.
- 기존 e2e 성능 사양(`dashboard-lcp-attribution`, `dashboard-cls`, 요청 예산 사양)이 지키는 계약은 유지한다.

### 5.4 기능 동일성 확인

- 각 변경마다 관련 단위·DOM 테스트를 돌린다.
- `typecheck`, `lint:boundaries`, `bundle:check`를 통과시킨다.
- 1단계에서 쓰던 실서버 점검을 한다. 대시보드 로드, 401 응답 0건, 지도와 뉴스 표시, CII·시나리오·Trip Assessment·채팅 분석·최신 브리프 동작을 본다.
- 마지막에 측정 장치의 상호작용 다섯 가지가 모두 결과를 표시하는지 확인한다. 결과가 표시되지 않으면 지연이 0이어도 실패로 친다.

## 6. 성공 기준 (기준선을 본 뒤 확정)

내 제안이며, 기준선 측정 후 주인과 숫자를 확정한다.

- **상호작용:** 다섯 조작 모두 입력에서 다음 그리기까지 중앙값 100ms 이하. 100ms는 사람이 즉각적이라고 느끼는 경계다.
- **로드:** 캐시가 있을 때 지도와 첫 화면 패널이 준비되기까지의 시간과 긴 작업 합계를 기준선보다 크게 줄인다. 목표 수치는 기준선을 보고 정한다.
- 반목표 세 가지에 해당하는 일이 없을 것.

## 7. 구현자에게 맡기는 것

- 측정에서 드러난 원인별 구체적인 수정 방법. 후보는 아래와 같지만, 측정으로 확인된 것만 한다.
  - 보이지 않는 패널 늦게 만들기
  - 브라우저 내 ML 작업자와 hls.js를 필요할 때 불러오기
  - 시작 시 데이터 요청 정리
  - `data-loader.ts`의 긴 동기 작업 나누기
  - 불필요한 다시 그리기 줄이기
- 측정 장치의 세부 구현: 셀렉터, 대기 조건, 출력 형식.
- 작업을 커밋 단위로 어떻게 나눌지.

## 8. 가 단계 결과

### 8.1 측정 방법과 주의점

- 3D 제거 전 코드(커밋 `b39f2850b`)와 제거 후 코드(`main`)를 같은 조건에서 연달아 쟀다. 순서는 다음과 같다.
  1. 이전 코드를 `C:\Users\tkddl\orca\wm-perf-old`에 `git archive`로 풀고, `globe.gl`(2.45.0)과 `three`를 따로 설치해 빌드했다. 서버는 주 체크아웃의 `.personal/store.ndjson`을 복사한 사본으로 3000번 포트에 띄웠다.
  2. 주 체크아웃의 측정 도구로 `baseline-rerun`, `baseline-rerun-cpu4`를 쟀다(각 5회).
  3. 이전 서버를 끄고 곧바로 현재 코드의 서버를 띄워 `no-globe`, `no-globe-cpu4`를 쟀다(각 5회).
- 같은 PC, 같은 시간대, 같은 데이터 저장소 파일, 같은 헤드리스 Chromium(GPU 플래그 포함), 같은 뷰포트(1600x1000)다. 수집기는 돌리지 않았다. `.personal/collect-state.json`의 마지막 수정은 2026-11-20 22:26이라 모든 측정보다 앞선다.
- 데이터 상태 정정: 수집기를 돌리지 않았다고 데이터가 고정되지는 않는다.
  - 내장 저장소는 키를 벽시계 시간으로 만료시킨다(`scripts/local/embedded-store.mjs:105`, `expiresAt <= now()`면 지운다). 저장소 파일을 복사해도 키는 시간이 지나면 사라진다.
  - 그래서 Task 3의 `baseline`(2026-11-20 17:53Z)과 재측정(2026-11-21 01:58Z 무렵)은 서로 다른 데이터로 잰 것이다. 8.10의 503 응답 다수도 만료된 키와 맞아떨어진다(원인은 확인하지 않았다).
  - 몇 분 간격으로 연달아 잰 재측정 쌍(`baseline-rerun`과 `no-globe`)은 데이터 차이가 작아 3D 제거 비교로는 공정하다. Task 3 열은 같은 데이터가 아니므로 참고용이다.
  - 나 단계는 자기 기준선을 다시 재야 한다. 그때 데이터 상태(수집기를 마지막으로 돌린 시각, 서버 시작 시각)를 함께 적는다.
- 한계: 서버 실행은 서로 다르다(이전 코드 서버와 현재 코드 서버). 측정 도구가 서버 실행마다 새 브라우저를 쓰므로 실행 간 흔들림이 있다. Task 3의 `baseline`을 참고 열로 함께 적어 그 흔들림을 보인다.
- `panelsReady`의 정의: 패널 격자에서 배치 순서로 앞의 데이터 패널 6개(화면 접힘과 상관없음)가 모두 로딩 표시를 벗어나 두 프레임 연속 그대로인 때다. 데이터가 그려진 상태와 오류 상태 모두 "벗어남"으로 친다. `live-news`, `live-webcams`(로딩 표시가 없는 영상 패널)와 `forecast`(개인 환경에서 로딩 상태가 끝나지 않음)는 뺀다. 실제로 쓰인 6개는 `insights`, `threat-timeline`, `strategic-posture`, `cii`, `strategic-risk`, `intel`이다. "첫 화면 전체 준비"가 아니다.
- 모든 측정에서 `failed`는 0이다.
- 개선 판정은 중앙값이 10% 이상 좋아지고 개선 폭이 두 측정 중 큰 쪽의 흩어짐(최댓값 − 최솟값)보다 클 때만 "개선"이다. 아래 모든 지표가 "차이 없음"이다.
- 3D 제거는 측정 결과와 상관없이 유지한다(주인 결정).

### 8.4 해석

- 3D 지구본은 지연 불러오는 청크(`GlobeMap`, 약 2MB)라서 평면 지도만 쓰는 이 환경의 처음 로드에는 원래 들어오지 않았다. 그래서 로드 지표(`jsBytes`가 0.3% 줄어든 정도)와 조작 지연 모두 거의 그대로인 것이 자연스럽다. 3D 제거의 이득은 코드·의존성 정리이지 속도가 아니다.
- 즉 성능 개선은 가 단계에서 나오지 않았다. 나 단계의 대상은 아래 느린 항목이다.

### 8.7 시간의 출처와 6절 성공 기준 제안 숫자 (기준은 `no-globe-v2`)

시간을 두 종류로 나눈다.

- **일부러 둔 타이머.** 바꾸는 것은 코드 속도가 아니라 동작의 선택이므로 주인이 정한다.
  - 지도 대기 3,500ms(+ 유휴 대기). 2MB 남짓한 WebGL 묶음(`deck-stack` 1.1MB, `maplibre` 1.0MB)을 첫 그리기와 긴 작업 측정 구간 밖으로 미루려고 둔 것이다. 줄이면 `mapReady`는 그만큼 줄지만 그 로드와 `initDeck`이 첫 화면 패널과 같은 시간대에 겹친다.
  - 검색 입력 디바운스 180ms(`SEARCH_DEBOUNCE_MS`). 측정은 마지막 키부터 재므로 `search.resultVisible`에 그대로 들어 있다.
  - 주소창 동기화 디바운스 250ms. 고친 레이어 지표에는 더 이상 들어 있지 않다.
- **실제 작업.** 코드를 빠르게 해서 줄인다. `mapAfterDemand`, 긴 작업 합계, 조작 결과에서 디바운스를 뺀 나머지다.

제안 숫자는 아래와 같다. "필요한 것"은 타이머를 바꿔야 하는지(주인 결정), 코드를 빠르게 해야 하는지를 적는다.

숫자는 제안이며 주인이 확정한다. 확정 전에는 나 단계로 넘어가지 않는다.

### 8.8 나 단계에서 먼저 손댈 후보

1. 지도 대기(`mapDemand` 약 3.7~3.9초): 코드 작업이 아니라 주인 결정이다. 그대로 둘지, 줄일지, 다른 신호(예: 첫 화면 패널 준비)로 바꿀지 정한다.
2. 지도 실제 작업(`mapAfterDemand` warm 0.9초, cold 1.7초): `deck-stack`과 `maplibre` 청크 로드, 스타일 불러오기, `initDeck`, 첫 그리기. 어느 것이 큰지는 나 단계에서 더 나눠 재야 한다.
3. CPU 4배의 긴 작업(`cold.tbt` 2.2초, `warm.tbt` 0.5초): `data-loader.ts` 등의 긴 동기 작업 나누기와 시작 시 요청 정리.
4. CPU 4배의 조작: country 350ms, panel 284ms, search의 디바운스 뒤 작업 약 142ms.
5. 레이어 다시 그리기는 CPU 보통 73ms로 이미 빠르다. 이전 판이 2순위로 꼽았던 것은 디바운스 때문이었다.

### 8.9 개선 판정 규칙의 흩어짐 조건 (주인 결정 필요)

- 현재 규칙은 "중앙값 10% 이상 개선, 그리고 개선 폭 > 두 측정 중 큰 쪽의 (최댓값 − 최솟값)"이다. 주인이 승인한 규칙이라 바꾸지 않았다.
- 문제: 처음 로드(`cold`) 지표는 5회 중 한 번씩 크게 튀었다. 예열 없던 `baseline-rerun`의 `cold.mapReady`는 5,678~10,374ms, `cold.tbt`는 101~1,369ms, `cold.lcp`는 92~1,736ms다. 이런 측정에서는 그럴듯한 개선도 "효과 있음"이 될 수 없어 진짜 개선을 되돌리게 된다.
- 이번에 넣은 예열 1회로 `no-globe-v2`의 흩어짐은 크게 줄었다(8.5). 다만 CPU 4배의 `cold.mapDemand`(5,356~5,722ms)나 `cold.panelsReady`(1,190~1,384ms)처럼 한 번 튀는 값은 여전히 나온다. 결과 파일에 회차별 값이 남으므로 이제 어느 회차가 튀었는지 볼 수 있다.
- 고를 수 있는 길(내가 고르지 않는다):
  1. 흩어짐을 튀는 값에 덜 민감한 방식으로 잰다. 예: 사분위 범위(IQR), 또는 최댓값 하나를 빼고 (최댓값 − 최솟값).
  2. 반복 횟수를 늘린다(예: 5회 → 9회). 측정 시간이 그만큼 늘어난다.
  3. 예열 1회를 넣은 지금 규칙을 그대로 쓴다.
- 고른 규칙은 6절의 목표 숫자와 함께 적는다.

### 8.10 실서버 기능 점검 (3D 제거 직후 코드, 3000번 포트)

헤드리스 Playwright(GPU 플래그, Basic 인증은 `loadEnvFile`로 읽고 출력하지 않음). 모두 통과했다.

- 대시보드 로드: 패널 86개. 401 응답 0건. 페이지 오류 0건.
- 지도: `deckgl-mode` 캔버스가 뜬다. 뉴스: 세계 뉴스 패널 20건, 실시간 뉴스 패널 표시.
- CII: 국가 클릭 시 국가 브리핑이 열린다(시리아로 확인).
- 시나리오: 공급망 패널에서 병목 지점을 펼치고 "Simulate Closure"를 누르면 상태가 "Active"가 된다.
- Trip Assessment: 포커스를 일본으로 정하고 포커스 막대의 초안 단추를 누르면 여행 위험 평가 대화상자가 열리고 내려받기 단추가 보인다.
- 채팅 분석: 질문을 보내면 분석가 응답이 돌아온다.
- 최신 브리프: 패널이 "WorldMonitor Brief. 12 THREADS"를 보여 준다.
- 설정 창에 2D/3D 전환 요소가 없다. 정정: 이 점검 당시 지도 설정 줄의 설명("Provider, theme and globe")과 검색어 "globe", NOTAM 도움말에 globe가 남아 있었다. 모든 언어에서 `d7c4e70e4`로 뺐다.
- `localStorage`의 `worldmonitor-map-mode`에 `"globe"`를 넣고 다시 열어도 평면 DeckGL 지도가 오류 없이 뜬다(값은 그대로 남고 읽히지 않는다).
- 무관한 사항: 부팅 중 `/api/telegram-feed`, `/api/x-feed`, `/api/oref-alerts`, 지진·불안정·기후 이상 등 `list-*` 엔드포인트가 503을 돌려주고 콘솔 오류가 55건 나온다. 3D 제거와 무관해 보이는 데이터 부재로 추정하며 원인은 확인하지 않았고 이전 코드와 대조하지도 않았다. 알려진 문제인 예측(forecast) 패널은 계속 로딩 상태이며 고치지 않았다.
